## 총평

Phase 분해는 자연스럽고, 기능 묶음도 실제 개발 순서와 대체로 잘 맞는다. 다만 현재 워크스페이스에 서버 구현이 전혀 없는 상태를 기준으로 보면 6주 일정은 다소 공격적이며, 테스트와 운영 검증 기준을 더 앞당겨 포함하는 편이 좋다.

## 확인된 강점

- 인증 → 상태 동기화 → 가챠 → 업적 → 운영 안정화 순서가 합리적이다.
- 각 Phase에 완료 기준을 둔 점은 좋고, Unity 연동 성공 여부를 기준으로 삼은 것도 실전적이다.
- 운영 안정화를 마지막 별도 Phase로 둔 점은 배포 전 체크리스트로 유용하다.

## 주요 피드백

1. 일정은 낙관적으로 보인다.
서버 신규 구축, Steam 연동, Unity 클라이언트 수정, 운영 환경 세팅까지 포함하면 `Week 1-6`은 여유가 거의 없다. 최소한 버퍼 주간이나 통합 테스트 주간을 하나 두는 편이 안전하다.

2. 클라이언트 수정 작업의 소유권이 별도 명시되어야 한다.
`SaveManager.cs`, `SariraSystem.cs` 수정 계획이 들어가 있는데 현재 저장소에는 해당 코드가 없다. 즉 이 마일스톤은 사실상 멀티 리포지토리 작업이므로, 서버 완료만으로 Phase 완료가 되지 않는다는 점을 더 분명히 써두는 것이 좋다.

3. 자동 테스트와 부하 검증이 늦게 등장한다.
현재는 기능 완료 기준이 주로 수동 연동 확인 중심이다. 최소한 Phase 1부터 인증, JWT, 마이그레이션, 헬스체크에 대한 자동화 테스트를 붙이는 기준을 넣으면 후반 리스크가 크게 줄어든다.

4. Phase 5의 운영 항목 중 일부는 앞당기는 편이 낫다.
헬스체크, 구조화 로깅, 환경변수 관리 정도는 초기 배포부터 필요한 항목이라 Phase 1 또는 2에 끼워 넣는 편이 실제 운영에 더 잘 맞는다.

5. 검증 포인트에 장애/복구 시나리오가 부족하다.
가챠 트랜잭션 실패, Redis 장애, Steam API 장애, DB 복구 같은 실패 시나리오 검증이 추가되면 운영 준비도가 높아진다.

## 권장 수정

- `Week 6` 이후 버퍼 또는 통합 테스트 주간 추가
- 서버 저장소 작업과 Unity 클라이언트 작업을 별도 트랙으로 명시
- `GET /health`, 구조화 로깅, 기본 테스트를 앞선 Phase로 이동 검토
- Phase별 성공 조건에 "자동 테스트 통과"와 "장애 시나리오 점검" 추가

## 2차 검토 (`v2.0`, 2026-05-03)

### 반영 확인

- Server / Client 작업 트랙이 분리되어 멀티 리포지토리 전제가 분명해졌다.
- `GET /health`, 구조화 로깅, 환경변수 관리가 Phase 1로 앞당겨졌다.
- 자동 테스트와 장애 시나리오 점검이 각 Phase 완료 기준에 포함되었다.
- `Week 7` 버퍼 주간이 추가되어 일정이 한결 현실적이 되었다.

### 남은 보완 사항

1. 클릭 어뷰징 방어 작업이 별도 태스크로 드러나 있지 않다.
현재 `/player/clicks`는 Phase 2 핵심인데, anti-cheat 설계가 이 기능의 핵심이므로 서버 검증 규칙 정의와 테스트를 별도 작업 항목으로 빼두는 편이 좋다.

2. 업적 비동기 동기화 정책 검증이 더 구체적이면 좋다.
Steam API 실패 시 "로컬 unlock은 성공, Steam sync는 지연"인지, 아니면 전체 실패인지 제품 정책을 먼저 확정하고 그에 맞는 테스트를 Phase 4 완료 기준에 넣는 편이 안전하다.

### 2차 판정

마일스톤 문서는 **실행 가능한 수준**까지 올라왔다. 남은 수정은 주로 세부 구현 리스크를 일정 항목으로 드러내는 정도다.

## 3차 검토 (`v3.0`, 2026-05-03)

### 반영 확인

- Phase 2에 클릭 어뷰징 방어 구현과 검증 기준이 명시되었다.
- Phase 4에 업적 비동기 정책과 저장 순서 검증이 포함되었다.
- 장애 시나리오 체크리스트도 2차보다 실제 구현 리스크에 더 가깝게 다듬어졌다.

### 남은 보완 사항

1. 세션 경합 시나리오 테스트가 있으면 더 좋다.
예를 들어 "새 기기 로그인 직후 기존 세션 로그아웃 요청" 같은 경합 케이스를 Phase 1 테스트 항목에 추가하면 단일 세션 정책 구현을 더 안전하게 검증할 수 있다.

2. 클릭 배치 지연 재전송 시나리오도 체크리스트에 넣을 만하다.
동일 `batch_id`를 60초 이후 다시 보내는 경우 이중 지급이 없는지 확인하는 테스트가 있으면 anti-replay 설계가 더 단단해진다.

### 3차 판정

마일스톤 문서는 **확정 직전 수준**이다. 남은 건 경합/재전송 같은 예외 테스트 케이스를 더 드러내는 정도다.

## 4차 검토 (`v4.0`, 2026-05-03)

### 반영 확인

- Phase 1에 세션 경합 시나리오 테스트가 추가되었다.
- Phase 2와 체크리스트에 `batch_id` 5분 이후 재전송 시나리오가 추가되었다.

### 남은 보완 사항

1. refresh 시 jti 교체 테스트가 있으면 더 좋다.
예를 들어 `POST /auth/refresh` 후 이전 JWT 재사용 시 401, 새 JWT는 200이 보장되는지 확인하는 테스트를 Phase 1 완료 기준에 넣으면 단일 세션 계약을 더 안전하게 검증할 수 있다.

2. 5분 이후 동일 `batch_id`를 새 배치로 간주하는 정책은 꼭 의도된 제품 결정으로 확인되어야 한다.
지금은 테스트 항목으로는 존재하지만, 이것이 "허용된 중복 가능 창"인지 "추후 보강 예정"인지 상태를 한 줄 더 적어두면 일정상 해석 차이가 줄어든다.

### 4차 판정

마일스톤 문서는 **거의 확정 완료**다. refresh jti 교체 검증만 추가하면 일정 문서도 깔끔하게 닫힐 수 있다.

---

## 5차 검토 (`v5.0`, 2026-05-03)

### 반영 확인

- Phase 1 완료 기준에 refresh 후 이전 JWT 401 / 새 JWT 200 검증이 추가되었다.
- Phase 2 완료 기준과 체크리스트에 `batch_id` 5분 이후 재전송이 의도적 허용 범위라는 점이 명시되었다.

### 남은 보완 사항

1. 현재 마일스톤 문서 기준 필수 누락은 없다.
이후 보강이 있다면 성능/보안 고도화 항목을 별도 백로그로 분리하는 정도다.

### 5차 판정

마일스톤 문서는 **최종 확정 가능 수준**이다.
