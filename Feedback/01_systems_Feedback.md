# 01_systems Feedback

- 검토 버전: `v1.0`
- 검토 일시: `2026-05-03`
- 원본 문서: [01_systems.md](/F:/stone_server/Goal/01_systems.md)
- 검증 범위: 문서 상호 정합성, 설계 타당성, Steam 공식 문서 적합성

## 총평

시스템별 목적과 흐름은 전반적으로 잘 끊어져 있고, 실제 구현 단위로 옮기기 쉬운 수준이다. 다만 인증과 상태 동기화 쪽에는 바로 수정해야 하는 설계 충돌이 몇 가지 있다.

## 핵심 확인 사항

- Steam 티켓을 서버에서 검증하고 이후 JWT로 세션을 운영한다는 큰 방향은 타당하다.
- 가챠를 서버 RNG와 단일 트랜잭션으로 묶는 설계는 어뷰징 방지 측면에서 적절하다.
- 시간 기준을 서버 UTC로 강제하는 방향도 문서 목적과 일관된다.

## 주요 피드백

1. Steam 인증 클라이언트 호출명이 잘못 잡혀 있을 가능성이 높다.
문서에는 `GetAuthSessionTicket()` 흐름이 적혀 있지만, Steam 공식 문서 기준으로 `ISteamUserAuth/AuthenticateUserTicket`에 넘기는 티켓은 `GetAuthTicketForWebApi()`로 발급받는 흐름이 맞다. 현재 표기대로 구현하면 인증 방식이 어긋날 수 있다.

2. 가챠 쿨다운 상태 코드가 API 문서와 충돌한다.
여기서는 "쿨다운 중이면 409 반환"으로 적혀 있지만 [03_api.md](/F:/stone_server/Goal/03_api.md)와 [04_milestones.md](/F:/stone_server/Goal/04_milestones.md)에서는 `429`를 기준으로 검증하고 있다. 한 가지로 통일해야 클라이언트 처리 분기가 흔들리지 않는다.

3. 시간 관련 필드명이 문서마다 다르다.
여기서는 `next_available_at`, DB 문서에는 `next_gacha_at`, API 문서도 `next_gacha_at`를 쓴다. 필드명은 스키마, API, 캐시 키 전반에 직결되니 지금 단계에서 하나로 통일하는 것이 좋다.

4. 인벤토리 동기화 설계가 "서버 권위" 원칙을 약하게 만들 수 있다.
클라이언트가 `delta`를 보내고 서버가 반영하는 구조는 구현 실수 시 치명적이다. 포인트 획득, 가챠, 업적 보상처럼 상태를 바꾸는 행위는 `/player/state` 일반 패치보다 명시적 서버 액션 엔드포인트로 나누는 쪽이 더 안전하다.

5. 업적 재시도 큐의 저장소가 문서 간에 엇갈린다.
여기서는 Redis List 기반 재처리를 말하고, DB 문서에는 `achievement_retry_queue` 테이블도 있다. 운영 단순성을 우선하면 한 곳을 주 큐로 정하고 나머지는 보조 감사 용도로만 남기는 식으로 정리하는 편이 좋다.

## 권장 수정

- Steam 인증 절차를 `GetAuthTicketForWebApi()` + `AuthenticateUserTicket` 기준으로 다시 표기
- 가챠 쿨다운 실패 코드를 `429` 또는 `409` 중 하나로 문서 전체 통일
- `next_available_at` / `next_gacha_at` 네이밍 통일
- `/player/state`를 범용 상태 변경 API로 두지 말고 도메인별 액션 API로 축소 검토

## 2차 검토 (`v2.0`, 2026-05-03)

### 반영 확인

- Steam 인증 절차가 `GetAuthTicketForWebApi()` 기준으로 바로잡혔다.
- `steam_id` 신뢰 원본을 Steamworks 검증 결과로 고정했다.
- 가챠 쿨다운 상태 코드와 시간 필드명이 `429`, `next_gacha_at`로 통일되었다.
- 범용 `PATCH /player/state`가 제거되고 도메인 이벤트 API 구조로 정리되었다.
- 업적 재시도 큐가 Redis 주 큐 + PostgreSQL 감사 기록으로 역할 분리되었다.

### 남은 보완 사항

1. `POST /player/clicks`는 아직도 클라이언트 자기신고 값에 크게 의존한다.
`count`만 받아 서버가 곱셈 계산하는 구조는 단순 delta 반영보다는 낫지만, 조작 클라이언트가 비정상적으로 큰 클릭 수를 임계치 이하로 쪼개 보내는 문제는 남아 있다. 클릭 빈도 상한, 서버 시각 기준 처리량 검증, 배치 시퀀스 번호 같은 추가 방어가 필요하다.

2. 업적 저장 순서가 더 명확해야 한다.
현재 흐름도는 Steam API 호출 후 DB 저장처럼 읽히는데, Steam API 실패 시에도 로컬 업적 상태와 멱등성이 유지되려면 `player_achievements`에 먼저 `steam_synced = false`로 기록한 뒤 외부 동기화를 시도하는 방식이 더 안전하다.

3. Redis 쿨다운 유실 시 복구 규칙이 시스템 설계 본문에 있으면 더 좋다.
마일스톤에는 Redis 재시작 시나리오가 들어갔지만, 실제 시스템 규칙에도 "Redis miss 시 DB `next_gacha_at`로 복구" 같은 우선순위를 적어두면 구현이 덜 흔들린다.

### 2차 판정

시스템 설계는 **대부분 안정화**되었다. 남은 핵심은 클릭 이벤트 검증 강화와 업적 저장 순서 명문화다.

## 3차 검토 (`v3.0`, 2026-05-03)

### 반영 확인

- 클릭 이벤트에 `batch_id`, 요청당 상한, 시간당 상한, 최소 전송 간격이 추가되었다.
- 업적 저장 순서가 `DB 선기록 -> Steam API 호출 -> 재시도 큐`로 명확해졌다.
- Redis 쿨다운 miss 시 DB `next_gacha_at` fallback 규칙도 본문에 반영되었다.

### 남은 보완 사항

1. 클릭 배치 재전송 방어의 보존 기간이 짧다.
현재 설계는 Redis `click:batch:{player_id}:{batch_id}` TTL 60초와 `last_click_batch_id` 1개 보조 값에 의존한다. 네트워크 재시도나 악의적 지연 재전송이 60초 이후에 들어오면 오래된 batch_id가 다시 처리될 여지가 남는다. 최소한 "최근 N개 batch_id 보존" 또는 "단조 증가 sequence 기반 검증" 중 하나를 문서에 추가하는 편이 더 안전하다.

2. 단일 세션 강제와 로그아웃 동작의 경합 처리 규칙이 있으면 좋다.
새 로그인과 기존 세션 로그아웃 요청이 거의 동시에 들어오는 경우, 현재 세션인지 확인한 뒤에만 `session:current:{player_id}`와 `refresh:{player_id}`를 삭제하는 compare-and-delete 규칙이 있으면 세션 꼬임을 줄일 수 있다.

### 3차 판정

시스템 설계는 **거의 확정 가능**하다. 남은 건 주로 재전송 방지 창과 세션 경합 처리 같은 경계 조건 명문화다.

---

## 4차 검토 (`v4.0`, 2026-05-03)

### 반영 확인

- 세션 경합 처리 규칙이 compare-and-delete 형태로 명시되었다.
- 클릭 `batch_id` 중복 방지 창이 60초에서 300초로 늘어나고, 그 의도도 문서화되었다.
- DB 문서와도 맞춰 `last_click_batch_id` 의존을 제거하고 Redis 기반 anti-replay로 정리됐다.

### 남은 보완 사항

1. `POST /auth/refresh` 시 jti 교체 규칙이 시스템 설계 본문에는 아직 명시되지 않았다.
단일 활성 세션 정책이라면 refresh로 새 JWT를 발급할 때 `session:{old_jti}` 삭제, `session:{new_jti}` 저장, `session:current:{player_id}` 갱신이 원자적으로 일어나야 한다. 이 규칙이 빠지면 만료 전 구 JWT가 계속 살아 있거나 current 포인터가 어긋날 수 있다.

2. `batch_id` 5분 창은 의도는 분명하지만 완전한 재전송 방지는 아니다.
문서대로면 동일 `batch_id`가 5분 뒤 도착하면 새 배치로 처리된다. 이건 명시적 트레이드오프라 이해 가능하지만, "5분 이후 지연 도착 패킷에 의한 중복 적립 리스크를 허용한다"는 점을 제품 정책으로 받아들이는지 한 줄 더 확인해두면 좋다.

### 4차 판정

시스템 설계는 **확정 직전**이다. refresh 시 jti 전환 규칙만 보강되면 사실상 확정해도 된다.

---

## 5차 검토 (`v5.0`, 2026-05-03)

### 반영 확인

- `POST /auth/refresh`의 `old_jti -> new_jti` 원자적 전환 규칙이 시스템 설계 본문에 추가되었다.
- `batch_id` 5분 창이 단순한 누락이 아니라 의도적 운영 타협임이 명시되었다.

### 남은 보완 사항

1. 필수 수정 사항은 사실상 해소되었다.
남아 있는 것은 refresh token rotation 같은 보안 강화 옵션이나, Redis 전체 유실 시 세션을 어떻게 복구할지에 대한 운영 정책 정도다. 이는 현재 설계의 모순이라기보다 추후 고도화 항목에 가깝다.

### 5차 판정

시스템 설계는 **최종 확정 가능 수준**이다.
