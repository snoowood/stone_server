# 03_api Feedback

- 검토 버전: `v1.0`
- 검토 일시: `2026-05-03`
- 원본 문서: [03_api.md](/F:/stone_server/Goal/03_api.md)
- 검증 범위: API 일관성, 보안성, 문서 간 충돌 여부, Steam 공식 문서 적합성

## 총평

엔드포인트 목록과 예시는 구현 착수용 초안으로 충분히 좋다. 하지만 인증 요청 형태와 상태 변경 API 설계는 보안 측면에서 먼저 다듬고 들어가는 편이 안전하다.

## 주요 피드백

1. `POST /auth/steam` 요청 본문에 `steam_id`를 받는 설계는 불필요하거나 검증 규칙이 추가되어야 한다.
Steam 티켓 검증 결과에서 실제 `steamid`를 얻을 수 있으므로, 클라이언트가 별도로 보낸 `steam_id`는 신뢰 대상이 아니다. 유지할 거라면 "서버가 티켓 검증 결과와 반드시 일치 비교" 규칙을 문서에 명시해야 한다.

2. 인증 흐름은 `GetAuthTicketForWebApi()` 전제와 함께 다시 적는 것이 좋다.
현재 문서 자체만 보면 어떤 클라이언트 Steam API로 티켓을 얻는지가 빠져 있고, 상위 문서에는 `GetAuthSessionTicket()`로 적혀 있다. 이 부분은 구현 오류를 부르는 대표 지점이라 API 문서에도 명시가 필요하다.

3. `PATCH /player/state`는 서버 권위 모델과 충돌 가능성이 크다.
`earn_points` 같은 delta를 클라이언트가 보내는 구조는 문서 목표인 위변조 방지와 맞지 않는다. 포인트 증가는 서버가 검증 가능한 이벤트에서만 계산하고, 클라이언트는 결과 조회 중심으로 두는 편이 훨씬 안전하다.

4. `402 Payment Required` 사용은 실무 상호운용성 측면에서 재검토를 권장한다.
포인트 부족을 표현할 수는 있지만, 많은 클라이언트/미들웨어가 402를 전제로 설계되지 않는다. `409`, `422`, 또는 `400 + 앱 에러코드` 조합이 더 일반적이다.

5. `ALREADY_UNLOCKED`는 에러보다 성공 케이스로 문서화하는 편이 낫다.
현재는 Errors 블록 안에 `200 ALREADY_UNLOCKED`가 들어가 있는데, 멱등 성공이라면 "성공 응답의 한 형태"로 분리하는 편이 API 소비자 입장에서 덜 헷갈린다.

6. 운영용 API가 마일스톤 문서와 완전히 연결되어 있지 않다.
마일스톤에는 `GET /health`가 있는데 이 문서에는 없다. 구현 우선순위가 낮더라도 API 카탈로그 문서에는 같이 올려두는 편이 좋다.

## 확인된 일치 사항

- `POST /time/sync`의 5분 초과 warning 규칙은 시스템 문서의 의도와 잘 맞는다.
- 가챠 상태 조회와 로그 조회 분리는 클라이언트 구현에도 유리하다.
- 업적 unlock을 서버 전용 API로 분리한 방향은 맞다.

## 권장 수정

- `/auth/steam`에서 `steam_id` 제거 또는 "검증 결과와 일치해야 함" 명시
- `/player/state` 수정 권한 축소 또는 도메인 액션 API로 재설계
- `402` 사용 여부 재검토
- `GET /health` 추가

## 2차 검토 (`v2.0`, 2026-05-03)

### 반영 확인

- `/auth/steam`에서 `steam_id`가 제거되었고 Steam 티켓 발급 방식도 명시되었다.
- `/player/state`가 읽기 전용으로 정리되고 `/player/clicks`로 도메인 이벤트가 분리되었다.
- `402`가 제거되고 포인트 부족 코드가 재정의되었다.
- `GET /health`가 추가되었다.
- 업적 멱등 성공 응답이 에러 케이스와 분리되었다.

### 남은 보완 사항

1. HTTP 상태 코드 표가 내부적으로 충돌한다.
`POST /gacha/pull` 예시에서는 포인트 부족이 `409 INSUFFICIENT_POINTS`인데, 하단 상태 코드 표의 `400` 설명에도 포인트 부족이 포함되어 있다. 둘 중 하나로 정리해야 한다.

2. `POST /auth/refresh`와 `DELETE /auth/logout`의 상세 요청/응답 스펙이 없다.
엔드포인트 표에는 있지만 구현 기준이 되는 본문 예시가 없어, 토큰 전달 방식과 성공 응답 형태가 팀마다 다르게 해석될 수 있다.

3. `GET /achievement/list` 상세 응답이 비어 있다.
클라이언트 화면 구현과 캐시 구조에 영향이 있으니 최소 응답 예시는 추가하는 편이 좋다.

4. `POST /achievement/unlock`에서 Steam API 실패 후 큐 적재 시 응답 정책이 명확하지 않다.
예를 들어 `200 { steam_synced: false }`로 둘지, `202 Accepted`로 둘지, 혹은 실패로 반환할지 정해야 클라이언트가 올바르게 표시할 수 있다.

5. `/player/clicks`는 여전히 보안 경계가 약하다.
서버가 count를 곱셈 계산하더라도, count 자체는 클라이언트가 주장한 값이다. anti-cheat 목적이 강하면 허용 최대치, 시간당 상한, 재전송 방지 규칙을 API 문서에 포함하는 편이 좋다.

### 2차 판정

API 문서는 **거의 정리되었지만 아직 확정 전**이다. 특히 refresh/logout/achievement list 상세 스펙과 업적 비동기 응답 정책은 구현 전에 고정하는 것을 권장한다.

## 3차 검토 (`v3.0`, 2026-05-03)

### 반영 확인

- 상태 코드 표와 `POST /gacha/pull`의 포인트 부족 코드가 일치하도록 정리되었다.
- `POST /auth/refresh`, `DELETE /auth/logout`, `GET /achievement/list` 상세 스펙이 추가되었다.
- 업적 비동기 응답 정책이 `steam_synced` 기반으로 명확해졌다.
- `/player/clicks`의 anti-cheat 규칙이 API 수준에서도 드러나게 되었다.

### 남은 보완 사항

1. `DELETE /auth/logout`는 현재 세션 확인 후 삭제한다는 조건이 한 줄 더 필요하다.
새 로그인과 구 세션 로그아웃 요청이 엇갈리는 경우를 막으려면, `session:current:{player_id}` 값이 요청 JWT의 jti와 일치할 때만 current session과 refresh token을 삭제한다는 규칙을 명시하는 편이 안전하다.

2. `POST /auth/refresh`의 장기 고정 refresh token은 탈취 시 리스크가 크다.
단일 세션 정책으로 범위는 줄었지만, 30일 동안 재사용 가능한 구조이므로 추후 구현 단계에서 refresh token rotation까지 갈지 여부를 별도 결정해두면 좋다.

3. `/player/clicks`의 batch 중복 방지 창이 API 문서만 보면 60초 수준으로 읽힌다.
지연 재전송까지 방어할지, 최근 N개 batch_id를 기억할지, sequence 기반으로 갈지 제품 정책을 한 번 더 고정하면 구현자가 덜 흔들린다.

### 3차 판정

API 문서는 **구현 시작 가능 수준**이다. 남은 리스크는 주로 세션 경합 처리와 refresh token 보안 강화 여부다.

## 4차 검토 (`v4.0`, 2026-05-03)

### 반영 확인

- `DELETE /auth/logout`의 compare-and-delete 규칙이 상세하게 추가되었다.
- `/player/clicks`의 batch 중복 방지 창이 300초로 명시되었다.
- refresh token rotation이 즉시 도입 대상은 아니지만, 보안 후속 과제로 문서화되었다.

### 남은 보완 사항

1. `POST /auth/refresh`의 jti 전환 동작이 API 문서에 아직 없다.
응답은 새 JWT를 주지만, 이때 기존 JWT가 즉시 무효화되는지, `session:current:{player_id}`가 새 jti로 교체되는지, old jti가 삭제되는지 명시가 필요하다. 단일 활성 세션 원칙상 이건 중요한 계약이다.

2. `/player/clicks`의 5분 창 정책은 replay 완전 방지가 아니라 명시적 운영 타협이다.
현재 문서는 이를 충분히 설명하고 있지만, anti-cheat를 강하게 기대하는 팀원이 읽으면 "동일 batch_id는 항상 중복 차단"으로 오해할 수 있다. "5분 이후에는 중복 방지가 보장되지 않음"을 더 직접적으로 적으면 해석 차이가 줄어든다.

### 4차 판정

API 문서는 **거의 확정 완료**다. refresh 시 old/new jti 처리 계약만 추가되면 확정해도 무리가 없다.

---

## 5차 검토 (`v5.0`, 2026-05-03)

### 반영 확인

- `POST /auth/refresh`의 jti 전환 계약이 API 문서에 명시되었다.
- `POST /player/clicks`의 5분 정책이 "5분 이내만 중복 보장, 이후는 의도적 허용"으로 더 직접적으로 선언되었다.
- 이전 라운드에서 남겨둔 계약 공백은 사실상 모두 닫혔다.

### 남은 보완 사항

1. 선택적 보안 강화 포인트만 남아 있다.
`refresh token rotation`은 여전히 유효한 후속 과제지만, 현재 API 계약을 불완전하게 만드는 수준의 누락은 아니다.

### 5차 판정

API 문서는 **최종 확정 가능 수준**이다.
